# 월간 사내 결제 랭킹 처리 절차

매월(또는 매주) SK일렉링크 사내 결제 데이터를 학동위키 DB에 반영하는 절차.

## 큰 그림

- **xlsx**: 사내 카드/제로페이 결제 내역에서 추출한 (사용처 / 사용처 주소 / 방문수)
- **자동 분류**:
  - **MATCHED** — DB에 같은 가게가 있음 → `회사장부`의 vote(YES) 추가
  - **ALIAS_MATCH** — 좌표 50m + 이름 유사도 ≥ 0.7 → 같은 가게로 단정, vote 추가
  - **REGISTRABLE** — 학동 일대 NOT_FOUND → 신규 Place 생성(`회사장부`가 등록자) + vote
  - **OUT_OF_AREA** — 학동 외(영등포·송파 등) → 무시
  - **GEOCODE_FAILED** / **NOT_FOUND_ADDR** — 주소 파싱 실패 → 운영자 검수
- **자동 효과**: vote(YES) 1표만 들어가도 `recomputePlaceAggregates`가 `crewVerified=true`로 갱신 → /map 카드·필터·마커에 ✓ 크루검증 띠

## 매월 절차

### 1. xlsx 파일 준비

`input/` 폴더에 `<월> <주차> 랭킹.xlsx` 형식으로 저장.

```
input/
├── 4월 4주차 랭킹.xlsx     ← 이미 처리됨
├── 5월 1주차 랭킹.xlsx     ← 다음 회차
└── ...
```

xlsx의 첫 시트에 다음 컬럼 필수:
- **사용처** — 가맹점 상호
- **사용처 주소** — 도로명 또는 지번
- **방문수** — 결제 건수 (숫자)

헤더 이름이 살짝 달라도 (예: "사용처명") 스크립트가 substring 매칭으로 잡습니다.

### 2. dry-run으로 검수

```bash
pnpm tsx scripts/apply-monthly-ranking.ts -- --file=input/5월\ 1주차\ 랭킹.xlsx
```

출력:
- 분류 통계 (MATCHED N / REGISTRABLE M / OUT_OF_AREA K …)
- `output/ranking-match-YYYYMMDD.csv` 생성

CSV를 엑셀로 열어서 확인:
- **MATCHED·ALIAS_MATCH** 행의 `db_name`이 실제로 같은 가게인지
- **REGISTRABLE** 행의 좌표가 학동 일대인지 (lat 37.51~37.52, lng 127.03~127.04)
- **OUT_OF_AREA** 학동 외 가게는 자동 무시 — 무시 OK

### 3. 의심 케이스 검수

흔한 케이스:
- xlsx 상호명에 회사명 + 가게명이 같이 들어감 (예: `화항풍국제무역（주） 알펜` ↔ DB의 `알펜호프`).
  - 이름 유사도가 0.7 미만이면 ALIAS로 안 잡히고 REGISTRABLE로 분류됨 → 같은 좌표에 가게 두 개 등록될 수 있음
  - 적용 후 운영자가 손으로 처리: 한쪽을 `/admin`에서 hide 또는 `/places/[id]/edit`에서 정리
- xlsx 상호명에 지점명이 빠짐 (예: `천미향` ↔ DB의 `천미향 논현직영점`).
  - substring 매칭으로 자동 잡힘 (score 0.85)

### 4. 적용

```bash
pnpm tsx scripts/apply-monthly-ranking.ts -- --file=input/5월\ 1주차\ 랭킹.xlsx --apply
```

수행 작업:
- **MATCHED·ALIAS_MATCH**: `회사장부`의 ZeropayVote(YES) upsert + `zeropaySelfReport=true` 보강 + recompute
- **REGISTRABLE**: 신규 Place 생성 + 첫 PlaceRevision + ZeropayVote(YES) + recompute
  - 카테고리는 이름 키워드로 자동 추정 (편의점→ETC, 커피→CAFE, 초밥→JAPANESE 등 — 다수가 KOREAN으로 default)
  - mealType=LUNCH 일괄
  - tags는 SK일렉링크 본사(논현동 83-15)에서 350m 이내면 `도보 5분` 자동
  - 메뉴·가격·추천이유는 비움 (크루가 위키 수정으로 채움)

### 5. 검증

```bash
# 전체 가게 수
curl -s "https://cosmic-gelato-23893c.netlify.app/api/places?mealType=LUNCH&pageSize=200" | grep -o '"id":"' | wc -l

# 크루검증 가게 수
curl -s "https://cosmic-gelato-23893c.netlify.app/api/places?mealType=LUNCH&crewVerified=true&pageSize=200" | grep -o '"id":"' | wc -l
```

또는 사이트에서 [✓ 크루검증] 칩을 누르고 갯수 확인.

### 6. 사후 정리 (선택)

REGISTRABLE로 등록된 가게는 메뉴·가격·추천이유가 비어있다. 운영자가:
- `/admin`에서 잘못 등록된 가게 hide
- `/places/[id]/edit`에서 카테고리·메뉴 등 보강
- 또는 크루가 자연스럽게 채워넣기 (위키식)

## 트러블슈팅

### "MATCHED인데 다른 가게로 잡힘"
- `findMatch`의 임계값 (`nameSim >= 0.55`) 상향 조정. `scripts/apply-monthly-ranking.ts` 약 71줄.

### "분명 같은 가게인데 REGISTRABLE로 잡힘"
- xlsx 상호명이 회사명·법인명 형태라 이름 유사도가 너무 낮을 때 발생.
- 적용 후 손으로 두 가게 중 하나를 hide.
- 또는 `findAlias`의 `sim >= 0.7` 임계를 0.6으로 내리고 다시 dry-run.

### "Geocode 실패가 너무 많아요"
- Naver Geocoding API 키(`NAVER_GEOCODING_CLIENT_ID/SECRET`) `.env` 확인.
- xlsx 주소 형식이 비정상이면 운영자가 직접 수정 후 재실행.

### "방문수 컬럼을 활용하고 싶다"
- 향후 "이번 달 핫플 랭킹" 같은 별도 표시로 활용 가능.
- 현재는 매칭 여부만 본다 — 방문수는 CSV에는 기록되지만 DB에는 안 들어감.

## 시스템 사용자

이 절차에서 만들어지는/사용되는 시스템 사용자:

| nickname | 역할 | 로그인 가능 여부 |
|---|---|---|
| `학동봇` | 네이버맵 크롤링으로 import한 제로페이 가맹점의 등록자 | 불가 (passwordHash 더미) |
| `회사장부` | 사내 결제 데이터로 검증·등록한 가게의 등록자/voter | 불가 (passwordHash 더미) |

두 사용자 모두 [추천 랭킹·검증 랭킹]에서 제외됨 ([lib/ranking.ts](../lib/ranking.ts) `EXCLUDED_NICKNAMES`).
